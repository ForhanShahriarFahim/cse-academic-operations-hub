# STU-01A — Student directory and roster enrollment

Issue [#37 STU-01](https://github.com/ForhanShahriarFahim/cse-academic-operations-hub/issues/37) · Approved · 18 November 2026 (Asia/Dhaka)

## Problem and outcome

Attendance administrators can add a student or import one group’s CSV today. They cannot search a private student directory, inspect a file before applying it, or enroll a batch from the list of students recorded for that batch. The manual form can change a global student record from a roster, while removing a student from the current roster also hides them from older session views. ATT-02 already protects existing identities on CSV import and reports committed outcomes. [Inspection evidence](verification.md)

Give authorized administrators a Students directory, a common CSV preview and confirmation flow for the directory and a selected class group, and ways to enroll one student or a whole eligible batch. Keep one student identity across departments and terms, with enrollment in each teaching group recorded separately. Preserve captured attendance when students join, leave, or become inactive. STU-01B retains Excel, roster exports in CSV/Excel, and printable roll-call. Attendance selection redesign, session lifecycle, marks policy, identity merges, historical corrections, and institutional rollout are separate work.

## Decisions for owner review

### D-1 — Private directory and scoped roster access

| Actor | Records and operations |
| --- | --- |
| Unscoped system or academic administrator | Use a dedicated `manage_students` capability with an explicit unscoped check for the all-department directory, identity create/edit/deactivate/restore, private phone on student detail, and directory CSV. Existing group authorization also applies to roster changes. Whole-batch enrollment requires both permissions. |
| Department-scoped system or academic administrator | Keep `manage_rosters` for groups in the course's authorized department. See current and inactive enrollments in that group, manage participation, and add by exact Student ID and name or import to that group. This can create a minimal identity on a new code. No global search, identity edits, private phone readback, or other-group history from this route. |
| Teacher assigned to the group | Keep authorized attendance and marks for assigned groups, using student ID, name, and attendance data. No directory, phone, identity, import, or enrollment controls. |
| Other roles, unassigned teachers and public users | The student and roster data described here require the explicit permissions above. |

Authorize before loading private records and on every direct read, preview, and write. Use the actual group and actor's current assignments. A department label on a student never grants access. Limit client payloads to the screen’s projection. Keep phone on authorized identity detail/edit only, and keep legacy notes out of the workflow. CSV mapping can show headings from the supplied file and previews can show its line numbers and safe outcomes. Phones, stored conflicting values, and raw rows stay out of preview results, receipts, audit payloads, and logs. Use request bodies for private search/upload input and keep it out of URLs, persistent browser storage, and public projections. [Authorization policy](../../../src/lib/auth/policy.ts) · [Project privacy decisions](../../decisions/INSTITUTIONAL_DECISIONS.md)

### D-2 — Directory, identity correction and lifecycle

- Add **Students** under Classes. Search by student ID or name, and filter by identity status, home batch (including no batch), and term. Default to all terms and active identities. The term filter uses actual enrollments in that term, including inactive enrollments. An all-terms search includes people without enrollments. Show the selected filters and distinguish no records from no matching results. Use deterministic pagination. Student detail shows identity and enrollment history by term, course, group, audience and enrollment status. Provide **Manage roster** on a current authorized group. Earlier groups are read-only here.
- Add and edit name, optional private phone, descriptive department and optional home batch. Treat Student ID as text, use the existing trimmed case-sensitive key, and preserve leading zeroes. Allow ID correction only before the identity has any enrollment or captured attendance. Keeping used IDs stable prevents an older roster file from recreating a student under a previous ID. Trim fields and reject blank required values and control characters. Reuse stored IDs for structured batches. Preserve existing structured department and legacy notes as stored. Where a legacy department label is absent, use the stored department reference as display context. Unknown department or batch stays blank. An existing inactive or graduated home batch remains visible on an identity; a new or changed home batch must be an existing active batch. A forged batch or duplicate ID gives a field error. Preserve stable internal IDs and the draft after a failed edit, and detect stale edits before applying them.
- Deactivate and restore identity only through named directory actions, with an explicit confirmation for deactivation that explains its effect across groups. Deactivation stops future attendance capture and new enrollment for the identity. Existing enrollment statuses stay as recorded, and only current active enrollments become eligible for new attendance again on restore. A previously removed enrollment still requires restoration in its group. Allow directory creation, corrections and lifecycle actions when there is no active term. Provide no hard delete or merge.
- A corrected name can appear when a historical screen joins the current student identity. Preserve IDs, enrollments, captured students, dates, recorded marks, and public snapshots. Displaying historical spelling as of a particular date would require separate historical identity data.

### D-3 — Manage one roster

- Keep **Manage roster** reachable from Attendance with its selected class group. Show canonical course/group, audience and active term before actions. List present roster membership and inactive enrollments, with inactive student identities indicated separately. Current roster membership for new sessions requires both an active student and an active enrollment. Keep typed input, group context, and useful focus on recoverable errors.
- **Add student** asks for exact Student ID and name, plus audience (`local`, `external`, or `merged`). Match an existing active identity by code and verify the name before enrollment. A new ID creates the identity and enrolls it in one transaction. Send mismatched or inactive identities to a directory administrator with a generic resolution message. An existing enrollment is a no-op on repeated Add. Offer explicit roster actions to change audience, remove membership, or restore an inactive enrollment. A scoped admin can use a member's roster row only for that group's enrollment changes. A directory editor can follow a separate **Edit student** link. Replace the manual action that currently writes both identity and enrollment on conflict or edit. Direct calls to legacy entry points must enforce the same boundary.
- Validate the exact group against the active term for every roster write, including removals and restores. A student from another department can enroll in the same group as local students. Keep one row per student, group and term, including after removal/restore. Audience belongs to that enrollment. Neither cross-department enrollment nor whole-batch enrollment changes a student's home batch, scheduling headcounts or group offerings.
- An already captured student remains visible and markable to authorized attendance users in that session after removal or global deactivation. Keep the current roster for new session creation and derive older session participants from captured attendance records. Keep summary denominators based on captured records and retain previous marks. An identity added after a session has no mark in it. [Attendance capture rule](../../architecture/ADR-001-academic-operations-boundaries.md)

### D-4 — Enroll a whole batch

- From **Manage roster**, show **Enroll a batch** to administrators with directory and group authority. Offer active home batches placed in the active term and linked through a non-cancelled offering for that exact group and course. For a merged group, select one actual linked batch per operation. Require an audience choice for new enrollment (`Local` or `Merged audience`). Cross-department exceptions can use the single-student or group CSV paths.
- Review actual students with that stored home batch. Display counts and student dispositions before a single confirmation. Create missing enrollments for active students. Count existing active enrollments as unchanged and preserve their audience. Exclude inactive identities and explicitly removed enrollments, with reasons. A batch with a planning headcount and no eligible student records produces no roster changes. A changed batch, group, candidate set or enrollment state requires a refreshed review. Confirmation is atomic with its audit and reports committed counts.

### D-5 — CSV mapping and dry run

- **Import CSV** from Students creates directory identities only. **Import CSV** from a selected roster can create an identity and enroll it in that group in one operation. Mapping Phone requires directory authority. For a scoped roster import, a phone column in an existing file defaults to ignored. The server rejects a forged phone mapping and does not use stored phone data to classify those rows. The current roster sample and aliases continue to work. The uploader chooses the file, verifies the column mapping, then selects **Preview import**. Auto-suggest known headings, require one-to-one mappings for Student ID and Student Name, and allow explicit mapping for optional Phone, Department and Home Batch. Roster mode also supports Audience Type. Ignore unmapped columns. Ambiguous auto-mappings require manual resolution.
- Use UTF-8 CSV with optional BOM, LF or CRLF, comma delimiter, and existing quote/escaped-quote behavior. Each record occupies one physical line. Count and report malformed input on its source line. Ignore blank lines. Support up to **500 nonblank data lines and 256 KiB** per file, checked on the server as well as in the picker. A blank/unknown required mapping, invalid encoding, or exceeded limit blocks the file. No data or audit writes during preview.
- A mapped batch cell can use `HSC: <label>` or `DIPLOMA: <label>` or a bare label with one known match across streams. Reuse the batch directory's label normalization. Unknown and ambiguous labels produce row errors. For a new identity, setting Home Batch requires directory authority and an active batch. A supplied batch for an existing identity is a match assertion. A blank optional field leaves existing values alone. Department remains descriptive, including for other departments. A matching existing identity is unchanged in directory mode and may be enrolled in roster mode. An inactive identity or conflicting supplied identity fields produce a safe row error. Later valid rows with a repeated ID are skipped after the first structurally valid occurrence, even if that first row later fails its database match.
- Keep ATT-02’s roster audience rule. A blank audience keeps the existing enrollment’s value or defaults a new row to local. An explicit valid value can change the audience, and a matching CSV row can restore an inactive enrollment. Mark both operations on the preview. Invalid audience, missing name, malformed rows, and identity conflicts show source line and reason. Keep rows in source order and label prospective outcomes **Created, Updated, Unchanged, Skipped, Failed**, with new identity versus existing student context where authorized. In directory mode, Created counts identities and Updated is zero. In roster mode, Created and Updated count enrollments, and restoring plus changing audience counts as one Updated row. [ATT-02 receipt rules](../ATT-02/spec.md#d-4--count-what-the-import-did)

### D-6 — Confirmation, stale data and audit

- Require a server-issued preview confirmation tied to the signed-in actor, mode, file and mapping, target group where applicable, active term and generation for roster work, and the state reviewed. Use the same write-free review/confirm pattern for a batch. Keep the file and review in the current page’s memory. Replacing inputs clears the preview, including for out-of-order responses. At confirmation, reauthorize and validate against transactional state. If data relevant to the preview changes, the proof expires, or any target/input/proof is mismatched, apply zero changes and prompt for a fresh preview. Failed/retired roster-import calls cannot bypass review.
- Confirm the reviewed eligible rows together. In a mixed file, **Import N eligible rows** makes the partial operation explicit. A preview with no eligible changes shows its results without a confirm action. Repeated or concurrent confirmation cannot duplicate rows or report uncommitted changes. Return the ATT-02-style receipt with committed counts, unchanged/skipped/failed counts and safe line-level reasons. Keep the file available after partial success and explain how to correct failed rows. On unexpected persistence/audit failure, roll back the attempted writes and show a recoverable failure.
- Audit committed mutations with actor, action, internal entity IDs, target context, and outcome counts or changed field names and statuses as appropriate. Store no raw PII or source rows in new audit fields. Do not emit mutation audits for a preview, stale or denied request, or no-op. Keep existing audit history and the existing roster CSV import event name.

### D-7 — Desktop and phone workflow

Use the portal’s existing page and form patterns. Keep directory filters and the roster's group context visible near their primary actions. Make directory results, roster controls and all preview rows readable at 320 px without page-wide overflow. Confirm near the outcome counts, announce results and errors, and support keyboard navigation, visible focus, labeled fields and safe cancellation. The workflow sketches cover directory and detail, group roster, batch review, CSV mapping/preview and the receipt. [Desktop and phone sketches](mockups/index.html)
