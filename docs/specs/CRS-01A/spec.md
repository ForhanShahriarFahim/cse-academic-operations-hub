## Outcome and scope

Authorized administrators can create a catalog definition, correct permitted fields, deliberately deactivate/reactivate it and inspect its changes. Everyone with internal viewing access can inspect the catalog/details. Existing offerings, merged audiences, attendance, allocation units, claims and publications remain intact.

Included: global catalog directory, create/detail/edit/history routes, lifecycle confirmations, impact evidence, permissions, stale protection, narrowly required assignment guards, forward revision migration, and disposable adapter/UI/history checks. Retain the current completeness report as the separate term section of `/courses`.

Excluded: offering creation/edit/cancellation/cloning (CRS-01B), group/audience/teacher/workload/coverage construction (CRS-01C), retrospective academic corrections, course versions/effective dates, automatic replacement/supersession or code reuse, permanent deletion, bulk import/export, curriculum/programme redesign, policy conversion controls, source reclassification, broader loader performance work (PERF-01), print redesign, institutional operations, dependency/bundler/runtime changes and remote synchronization. New courses intentionally have no offering, group, allocation, coverage requirement or meeting; say so after creation.

## Required behavior

### Fields and validation

Server validation is authoritative. Accept each supported field once as text; reject malformed IDs/revisions and repeated/file values. Ignore unrecognized business fields; they must not mutate state, actor or audit metadata. Preserve input on expected errors. Validate only changed academic values on legacy rows, so unchanged unsupported data does not prevent a valid title correction.

| Field | New/changed value contract |
| --- | --- |
| Code | Trim/uppercase; 2–8 ASCII letters, hyphen, four digits, optional single uppercase suffix in parentheses: `^[A-Z]{2,8}-[0-9]{4}(\([A-Z]\))?$`; maximum 16 characters. Accept either one separating space or a hyphen at entry and show the canonical candidate before save; reject other internal whitespace. Preserve suffix. Unique by `upper(btrim(code))` across active/inactive IDs and known audit aliases. Existing nonstandard codes remain displayed unchanged. |
| Title | Required plain text, 1–200 trimmed characters; preserve internal punctuation and spacing; escape output. No type detection. |
| Academic credits | Required plain decimal, greater than zero and at most 999.9, at most one decimal place; normalize to one decimal. Reject signs, exponent, commas, NaN, extra precision and blank; never silently round. Range is the current storage limit, not an institutional recommendation. No default to 3/2 or coupling to type. |
| Type | Explicit `theory`, `sessional`, `thesis`; UI label “Thesis or project” for the existing `thesis` token. No new type tokens. Existing unsupported type is read-only and labelled. |
| Owning department | Existing department ID or explicit Unknown (`null`). No auto-CSE default; no department creation or inference from prefix. New user must deliberately choose a department or Unknown. |
| Curriculum semester | Required integer 1–8, chosen explicitly; do not derive from the course number or active term. |
| Lab / specialist requirement | For a new/academically edited unused sessional, `needsLab=true`; for theory/thesis, `false`. Show the derived flag. Optional specialist choice: None, `computer`, `microprocessor`, `networking`, `laboratory`, with existing rule explanations. Preserve unchanged legacy tokens/flag mismatches, visibly flagged; no automated repair. A specialist requirement is checked independently by existing suitability rules. |
| Status / revision | New course is Active. Status changes use the lifecycle action, never the edit payload. Positive integer revision is an opaque stale token. No user-supplied actor/time or mutable draft/deletion flag. |
| Change reason | Required 1–300 trimmed plain-text characters for edits and lifecycle changes; optional on create. Ask for an administrative reason without personal/student details. No-op edits/transitions do not require a fresh event or bump revision. |

Keep canonical comparison separate from stored legacy values. Existing duplicate canonical codes stay separate and flagged. New/renamed codes cannot collide; unchanged-code title/lifecycle changes remain possible. Audit aliases reserve earlier codes against assignment to another course; self-reversion is allowed only while unused and collision-free. No fuzzy/substring code matching.

### Directory, detail and forms

- `/courses` keeps **Courses & offerings**. Put a clearly global **Course catalog** section first, then **Scheduling completeness — [active term]**. Catalog works with zero active term; the completeness section explains that an active term is needed. Ambiguous/unavailable context must not make the global directory choose a term silently. Use an independent authenticated catalog loader, not `getPortalData()` as its prerequisite.
- Catalog supports case-insensitive code/title search and Active / Inactive / All status filter, default Active. Count means displayed catalog records, never active-term offerings. Show code, title, academic credits, type, owner, curriculum semester, requirement and status. Link codes to details. Omit the misleading Groups column; retain group counts/status in the separate term report. Mobile uses readable cards and stacked filters. Filters persist in the URL/return link.
- Editors see **Add course**, Edit and lifecycle actions; other viewers receive no management/history payload. `/courses/new`, `/courses/[id]`, `/courses/[id]/edit` and `/courses/[id]/history` follow existing directory patterns. Authorize before reading editor data, including direct history/actions.
- Detail separates catalog facts from **Recorded use** (editor-only all-term impact list) and **Workload is assigned per teaching group** explanation. Show known credits as academic credits; never put a workload input on the catalog form. After create: “Course added. No term offering or teaching group has been created.”
- Edit shows frozen academic fields with the exact reason and named recorded uses; server refuses a crafted change to a frozen field. Unsupported values remain visible. On changed title with recorded use, show old → proposed title, affected terms/group/offerings, historical-working-title notice and immutable snapshot/claim notice; require **Apply this title correction to live records** acknowledgement.
- Recompute impact and candidate on submit under the lock. Bind acknowledgement to course ID/revision, normalized candidate and actual reference evidence via server fingerprint; changed evidence requires review again. No force-save for blockers. Do not trust counts, booleans or warnings supplied by the browser.
- Loading shows labelled placeholders; empty catalog/filter explains the state and provides editor add/reset links. Missing record has not-found/back link. Pending disables repeated submit and announces Saving. Success preserves useful context and links detail/back to catalog. Errors use field associations, summary/focus and standard result messages; no raw SQL. Stale says “Someone else changed this course. Review the latest values before saving.” Preserve input for copying; explicit Reload latest replaces it. Revoked access returns a permission result; no mutation or history disclosure. Distinguish retryable unexpected errors from expected conflict/stale/denied outcomes. Use the existing dirty-form/discard pattern.
- History is editor-only, newest first, 20 events/page with validated per-course cursor. Show Asia/Dhaka time, actor display name, action, changed fields, old/new values, reason and acknowledged impact. No fabricated baseline events for imports; explain when no catalog-management history exists. Keep audit events when inactive. Exclude actor email/private fields and unrelated events.

### Recorded-use protection and lifecycle

Determine use by stable course ID in **every** offering and group, regardless of term/status. Descendant attendance/enrollments/allocations/meetings inherit the group reference; include human-readable term, audience and aggregate counts without private student names. Count a merged group once; list offering count separately. Scan every saved schedule-version snapshot, including archived/draft versions and catalog-only metadata, using supported structured shapes and exact code aliases; IDs when present. Include exact-code claim snapshots even when a legacy claim has no group link; claims alone are retained historical evidence, not a new teaching obligation. Never match substrings or count draft exports as published. Unsupported/malformed/ambiguous stored snapshots are uncertainty: block academic edits and deactivation conservatively, explain why; title correction is still possible because no saved payload is rewritten. Do not claim an unknown match proves use of a particular course.

For academic edits, **any** recorded use freezes D-3's fields. For lifecycle, inspect term status and offering state, not dates: a cancelled/completed offering by itself is historical; any group in a term other than explicitly completed blocks, even if linked offerings are cancelled or it has no meetings. An unknown offering status blocks deactivation even in a completed term until resolved. A completed-term group may remain; an inconsistent descendant in another noncompleted/unknown term blocks. Saved snapshots alone do not create teaching obligations, but uncertainty about their shape blocks lifecycle. Show recorded history separately from blockers, not as one alarming total. The conservative rule can require future offering/group workflows before a course is deactivatable; A adds no cancellation escape hatch.

Deactivate/Reactivate detail review shows current status, reason, actual impact and a deliberate confirmation naming the course. Bind confirmation to ID/revision/command/evidence fingerprint; refetch on changed evidence. Reactivation creates no offering/group/enrollment or publication and does not repair imported facts. Already-in-state commands are successful no-ops after permission/revision checks.

Inactive courses stay visible in detail/history/All/Inactive and all existing referenced working records. Do not filter them out of `getPortalData()` or strip groups/attendance. Add the status field to the serialized course view. New canonical meeting creation (manual and automatic) must reject an inactive/missing course inside the authoritative transaction, even with a stale or forged group selection. Existing completed history still renders; no automatic meeting deletion or claim/attendance change. Future offering/group creation in CRS-01B/C must take the same context lock, verify active course, and use the stable ID. Seed/recovery fixtures are operator paths, not portal authority to bypass lifecycle.

### Transactions, migration and preserved history

Catalog mutation entry points authorize `manage_catalog`, then start a standalone transaction acquiring **exclusive term-context lock first**, then the course row. Do not enter through `activeTermWrite` and upgrade its shared lock. This global directory does not need an active-term token or increment the term generation. Re-read revision, candidate and all-term evidence; write change and `course.create/update/deactivate/reactivate` audit atomically. Audit failure rolls back everything. Sharing this lock with existing writers serializes title edits/deactivation with publication/assignment reads. Multiple browsers still require database serialization; Next client sequential dispatch is not concurrency protection.

Migration: next available forward migration (currently `0018`, recheck before implementation) adds positive `revision` default 1 without changing IDs, codes, titles, credits, flags, ownership, source files or relationships. Add a non-unique canonical-code lookup index; tolerate existing duplicates and enforce new collisions under the exclusive writer lock plus existing exact-code uniqueness. Do not add global academic CHECK constraints that reject legacy rows or silently backfill different facts. Reuse independent `audit_events`; no invented historical course edits. New helpers take an injected reader/transaction and use type-only DB imports; extend the database-free import guard so inspection/tests cannot initialize configured storage accidentally.

Disposable populated PGlite/PostgreSQL migration and recovery checks must prove unchanged domain rows/snapshot bytes apart from the added revision and schema/index metadata. Test from the documented `0009` populated baseline through the full forward chain and from current `0017`, including BUG-25 refusal on inconsistent data. Never skip or apply migration `0017` as part of this institutional task: any eventual institutional rollout requires a separately authorized cold backup/migration with preflight. No reset, configured-client import, startup or migration is needed to review this proposal.

Title edits intentionally alter live label projections; they must not alter stored offering/group links, attendance/session values or calculated marks, allocation units/eligibility/payment, claim snapshots, saved schedule-version payloads, published CSV/screen/print bytes or unrelated audits. Show current title on live reports and captured title on immutable outputs consistently. Revalidate affected internal label/report routes after commit, before redirect; catalog edits never republish. Retain existing Courses print coverage/catalog behavior with corrected headings and active/inactive status visible; management/filter controls do not print. Check A4 parity, no new print/export feature.
