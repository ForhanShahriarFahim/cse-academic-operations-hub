## Outcome and scope

An authorized user opens a draft or active term's class groups, sees every offering that still has no class group, and creates a class group for one cohort or one merged class for several cohorts of the same course. They assign teachers with explicit workload units and set the weekly requirement, and can later change teachers, units and the requirement, or remove a group that was never used. Every internal viewer can read the list and its completeness. In the active term a finished group is ready for the existing Routine builder and auto-schedule.

Included: a term-addressed class-groups page with completeness and filters; create, edit and remove for one class group at a time; reasons, stale protection and audit; a change history; links from the term page, the offerings page and Courses & offerings; disposable adapter, concurrency and browser checks.

Excluded: starting a whole term's class groups from the previous term and comparing teachers between terms (proposed as CRS-01D, see D-1); scheduling, rooms and meeting teachers (existing Routine builder); scheduling a draft term before activation; splitting one cohort into sections; cross-listed classes that join different course codes; changing a group's course; a cancelled/closed state for groups that already have classes or attendance; enrollment, attendance and extra-load records; external commitments (OD-01); policy rules that compute units; bulk import/export; schema migration (D-8); institutional operations, pending migrations `0017`/`0018`, dependency/bundler changes and remote synchronization.

| D-1 — Slice boundary | This slice manages class groups **one at a time**. “Start this term's class groups from the previous term”, with a carried/changed-teacher comparison, is the next slice (CRS-01D). | Keeps this delivery reviewable and settles the rules first; the bulk step then reuses them. The cost: until CRS-01D, preparing a whole new term means creating each group by hand. Alternative: build both together as one larger delivery. |
| D-2 — Editors | New capability `manage_class_groups` for system administrators, academic administrators and routine coordinators, in CSE planning scope. Everyone else with internal access is view-only. | Coordinators own teacher assignments in the role table and cannot schedule without a group. Consequence to accept knowingly: units feed extra-load eligibility, so coordinators would be able to change a figure that affects payment eligibility. Alternative: administrators only. Change history is editor-only. |
| D-3 — Which terms | Editable in **draft** and **active** terms, addressed by term ID; completed and legacy-status terms are read-only. | Same rule as offerings. In a draft term groups can be prepared but not scheduled: the Routine builder serves the active term only, and that does not change here. |
| D-4 — Audience | A class group belongs to one course and one term and has one or more of that course's offered (planned or open) offerings in that term. Two or more offerings make a **merged class**. An offering belongs to **at most one** class group. An optional outside audience (label and student count, count may be unknown) can be recorded. | “At most one” rules out splitting a cohort into lab sections for now; if the department does that, it needs its own decision. The rule is enforced by the store under the term lock, not by a database index (D-8). Cohorts are never merged: each keeps its own offering. |
| D-5 — Teachers and units | Zero or more **active** teachers per group; zero is allowed and shown as a vacancy. Each teacher has explicit units (0.25–20.00, two decimals). With several teachers the editor chooses **each credited in full** or **split between them**; nothing is computed silently. A merged class counts once per teacher, not once per cohort. | The form suggests units and always shows where the suggestion came from: the last recorded units for this course, otherwise catalog credits for theory and 2.00 for a one-credit sessional (the recorded current practice); otherwise blank. The suggestion is never saved without the editor seeing it. How shared classes *should* be credited is an institutional rule this slice does not assert. |
| D-6 — Weekly requirement | Fixed delivery needs meetings per week (1–14) and weekly minutes (30–1,500); teacher-managed delivery (thesis/project) has neither. It can be marked provisional. Suggested from the most recent group of the same course when one exists, otherwise blank. | Auto-schedule and completeness already depend on these values. No contact-hour rule is invented from credits. |
| D-7 — Changes after first use | Teachers, units, requirement, outside audience and notes can change at any time in a draft or active term. The **course never changes**. The **audience** can change only while the group has no scheduled class, enrollment, attendance session or extra-load record. A teacher who still teaches one of the group's scheduled classes cannot be removed from the group until that class is changed. **Remove** deletes the group, its links, requirement and allocations, and is allowed only when it has none of those four kinds of records; its offerings stay. | A used group cannot be closed or removed in this slice; that needs a stored state (D-8). Imported Summer 2026 groups all have classes, so their audience is fixed here: two of them cannot be merged without first clearing their classes. |
| D-8 — No schema change | Keep all four tables as they are. Stale protection uses a server fingerprint of the group and its links, requirement and allocations; reasons, actor and before/after go to the existing audit log. The store keeps exactly one requirement row per group and one allocation per teacher and group. | No migration and no institutional rollout step. Costs: “one group per offering” and “one allocation per teacher” are rules in code, not constraints; a group has no cancelled state. A group that already breaks these rules (several requirement rows, duplicate allocations, a link to another course or term) is shown as needing reconciliation and is read-only here. |

## Required behavior

### Class groups page

- Route `/terms/[id]/groups`. Title **Class groups — [term name]**, with the term's lifecycle and, when it is not the active term, the statement that viewing it does not change the active term. Linked from the term page, the term's offerings page and Courses & offerings.
- Summary: class groups, merged classes, without a teacher, without a weekly requirement, offerings without a class group and, in the active term, not yet scheduled.
- One row per class group, ordered by course code then audience: course code and title, type, audience (each cohort with its semester; “Merged class” when several; outside audience when recorded), teachers with units and the crediting method, weekly requirement, and state badges: Vacancy, No weekly requirement, Provisional, Teacher-managed, Needs reconciliation, and in the active term the existing scheduling status. Inactive teachers and cancelled offerings still attached are flagged.
- A separate **Offerings without a class group** list, by cohort, each with **Create class group** (editors) carrying that offering into the form.
- Filters kept in the URL: stream, cohort, teacher, state, and code/title search. Mobile uses stacked cards with no page-wide overflow. Printing shows the lists without controls.
- Empty and blocked states: no offerings in this term (link to term offerings); every offering has a group; read-only term; missing or ambiguous term returns not-found.

### Create and edit

- Create: `/terms/[id]/groups/new`. Choose the course from those with at least one ungrouped offered offering this term; tick the cohorts (each ungrouped offering of that course). Two or more ticks state plainly: “One merged class for N cohorts. The cohorts stay separate.” Offerings already in a group are listed as unavailable with the group that holds them.
- Delivery: fixed weekly classes, or teacher-managed (default for thesis-type courses). Weekly requirement per D-6.
- Teachers: add rows of teacher and units. Each row shows the teacher's current total for this term and the total after saving, and a non-blocking note when it passes that teacher's advisory limit. With two or more teachers the crediting choice (D-5) is required. Inactive teachers cannot be added.
- Outside audience: optional label (up to 40 plain-text characters) and count (blank means unknown). Notes: up to 500 plain-text characters, no student details.
- Edit: `/terms/[id]/groups/[groupId]` shows the same form with the course fixed and, when D-7 fixes the audience, the audience shown read-only with the reason. A reason (1–300 plain-text characters) is required for every change to an existing group and optional on create.
- In the active term the form states the consequences before saving: workload totals and extra-load eligibility follow the new units at once; existing extra-load records and published routines are not changed; a teacher's access to this class group follows their assignment.
- After saving in the active term the group page offers **Schedule in Routine builder** and notes that auto-schedule picks up unscheduled groups that have a teacher and weekly minutes. In a draft term it says scheduling opens when the term is activated.
- Remove: on the group page, with the typed course code and a reason, per D-7. A group that cannot be removed lists what it has (for example “3 scheduled classes, 2 attendance sessions”).
- Server validation is authoritative: each field once as text, malformed IDs refused, unrecognized fields ignored, browser-supplied totals and flags never trusted. Expected errors keep the user's input and place. Pending disables repeat submits and announces progress. Stale says “This class group changed since you opened this page. Review the current details before saving.” Forms submit without React's automatic form reset (the CRS-01B correction).

### Permissions, transactions and preserved history

- Every action authorizes `manage_class_groups` on the server before reading editor data. Viewers receive no editor payload or history. Revoked access returns a permission result with no change.
- Each mutation is a standalone transaction: shared term-context lock first, then the term row locked for update, then a re-read of term status, the offerings and their links, the course, the teachers and the group's dependent records before deciding. This serializes with offering, catalog, cohort and rollover writers and with other class-group editors of the same term. Teacher rows are locked so a teacher cannot be deactivated between the check and the save.
- Audit events (`class_group.create`, `class_group.update`, `class_group.remove`) record actor, term, course, audience, before/after teachers with units and method, requirement, outside audience and the reason. Audit failure rolls back the change. A save that changes nothing writes no event. Removal keeps its event, which names the course and audience.
- A change history per term (editor-only, newest first, paged) lists these events.
- Nothing in this slice writes to offerings, meetings, meeting teachers or rooms, enrollments, attendance, extra-load records, schedule versions, placements, courses, teachers, external commitments or their allocations, or any other term. Published snapshots and their CSV/print output are unaffected.
- The offerings page keeps its rule (an offering in a class group cannot be cancelled or removed) and now links to that group; removing an unused group makes the offering changeable again.
