## Problem and inspected baseline

The batch page is a read-only active-term table. It lists every batch, including those without a placement, uses `Sem ?` for absence, and derives shared delivery from meetings rather than all teaching-group memberships. There is no cohort editor, lifecycle action, placement history or count confirmation workflow.

`batches.student_count` is global; `batch_term_placements` stores only batch, term and semester. `getPortalData`, meeting serialization, scheduling and room transaction evidence all read the global count. A change therefore affects live drafts in every term. There is no verification date, actor or source. Existing unique indexes distinguish HSC-22B from Diploma-22B and allow one placement per cohort/term. Semester 1–8 is a schema comment, not a database check.

The checked-in Summer seed sets every cohort count to null. This is seed evidence, **not a census of institutional storage**. Synthetic safety fixtures contain non-null counts and two-term progression/repeat examples; their comment explicitly disclaims institutional lifecycle decisions. Absence of a placement does not establish graduation. No institutional database was opened during this inspection.

## Outcome and scope

An authorized administrator can maintain a cohort, manually place it in the active term, confirm that term's count, and inspect all placement/change history. Earlier placements and approved publications remain intact. Lifecycle restrictions explain what must be resolved rather than deleting academic records.

Included: create/edit identity, deactivate/reactivate/graduate/restore, tightly guarded unused-record deletion, active-term manual placement and unused-semester correction, term-specific count capture/verification, historical inspection, audited stale-safe actions, consistent downstream count/confidence projections, and forward migration on disposable adapters.

Excluded: next-term wizard or draft-term placement editing, automatic progression/copying, per-term hold/repeat overrides, time-grid cloning (BAT-01B); student/roster imports (STU-01); catalog/offering construction (CRS-01); degree eligibility/certification; historic-term correction authority; new public contact disclosure; institutional migration/rollout; build/runtime repairs; remote synchronization. No print/export product is added for the directory. Existing routine/teacher/official/CSV outputs are regression surfaces.

Dependencies: accepted SET-01A term-context protocol and existing history/publication protections. Parent #6 stays open after A. The owner must approve D-1–D-6 below before application code or migrations.

## Required behavior — proposed decisions

### D-1 — Identity, authority and retention

- The current application manages CSE cohorts in HSC or Diploma streams. This slice adds no programme/department selector or inferred programme migration. Identity is stream + batch label; intake and sort order remain metadata.
- All internal viewers may read the directory and placement history. Add `manage_batches` only to system and academic administrators, honoring existing global/CSE department scope. Coordinators, teachers, viewers, other-department-only administrators and anonymous users cannot mutate through direct requests. Full change/audit detail and count source/actor metadata require `manage_batches`; public projections never receive them.
- New labels trim outer whitespace, collapse internal whitespace and compare case-insensitively within the stream, including retained inactive/graduated records. Preserve ordinal/suffix distinctions; do not infer labels from numbers. Label 1–40 characters, intake at most 120, signed 32-bit integer sort order; reject blank/control-character labels and unknown fields/actions. Stream is exactly HSC or DIPLOMA. Audit reasons are trimmed, 1–300 characters. No individual student data belongs in reasons or count sources.
- Stream may be corrected only before any academic/snapshot use; thereafter explain that a different stream needs a separate cohort. Label/intake/order corrections remain possible with a reason and revision. Existing relational references keep the same cohort ID. Placement history is headed by current identity and explicitly identifies renames through the change log; it must not claim that a historical label was stored on the old placement. Frozen publication/claim labels are never rewritten.
- Migration retains existing identities/status strings exactly, including legacy duplicates under the new comparison. Do not silently merge/rename them. New creates/renames cannot introduce another normalized collision; unrelated edits remain possible. Unknown legacy statuses are displayed verbatim and management refuses lifecycle/placement commands until a separately approved resolution; identity corrections and history reading remain possible.
- Permanent deletion is available only for a newly created unused mistaken record. Existing imported records are retained. Any placement, representative, window, day plan, home-student reference, offering, group/meeting/attendance descendant or saved snapshot reference blocks deletion, regardless of status/term. Parse supported snapshots structurally using IDs and recorded label aliases; unsupported/ambiguous saved evidence blocks deletion conservatively. Preserve the deletion audit as an independent tombstone; do not delete change history. Preview and transaction both check the full reference inventory.

### D-2 — Manual placement and truthful history

- Directory/detail work without any active term. Identity editing and safe lifecycle actions remain available; active-term placement/count controls explain the missing/unavailable term. URL selection never activates a term.
- Show one chronological row for every existing placement, with term name/status, curriculum semester and term-specific count state. No row means **Not placed**, never graduated, Semester 0 or an invented repeat. Earlier/unknown-status terms are read-only. History lists all retained cohort states; lifecycle does not hide historical attendance/routines.
- An active cohort may be manually placed in the explicitly captured active term at semester 1–8. Creation is separate from identity creation and count confirmation; it never creates an offering, enrollment, meeting or grid. A missing placement starts with unknown count, not the global legacy number. Duplicate/stale requests cannot replace a placement.
- Correct an existing active-term semester only while it has no term-specific offering/group/meeting/enrollment/attendance/publication use. Compare before/after and require a reason; retain its prior semester in the audit. There is no placement deletion or historical editing in A. Existing out-of-range legacy semesters survive migration and are flagged; the new write constraints prevent new invalid values without pretending legacy values were valid.
- A draft-term placement in existing data is visible but read-only in A. Preparing a destination term and repeat/hold decisions belong to BAT-01B. Completed placements retain their original semesters and counts when the active term changes.
- Derive **Shared teaching** from linked teaching-group offerings and external audience membership in the selected term, even if not scheduled. Count it as a delivery attribute, separate from cohort lifecycle and count verification. Do not merge cohort identities or infer shared membership from labels.

### D-3 — Lifecycle, graduation and hold semantics

- New identities start active. Supported planning states: active, inactive and graduated. Deactivate means suspend new placement/selection until explicit reactivation. Graduation is an administrator's explicit cohort planning disposition, with a reason; it does not certify degrees, alter individual student status, remove enrollments or follow automatically from semester 8, dates or missing placement. Inactive is not a term-specific hold.
- Active → inactive, active/inactive → graduated, inactive → active, graduated → active (explicit **Restore cohort**, with reason and confirmation). No automatic transition and no graduated → inactive shortcut. No-op commands create no duplicate audit/revision. Graduate/deactivate/restore/delete show fresh impact and require deliberate confirmation. Restoring grants no placement or count automatically.
- Refuse deactivate/graduate while unresolved planning/teaching use remains in any term not explicitly completed: any placement in a draft term; planned/open offering; active canonical meeting/group-linked enrollment; or active enrollment for a home-cohort student. Inspect all terms, including dates already past: a past date alone does not establish completion. Unknown term/offering/enrollment states or ambiguous use fail closed with an explanation. Historical completed-term use and a bare active-term placement without ongoing obligations may remain. Identity-linked students alone do not prove an ongoing enrollment and are preserved unchanged.
- The fresh impact view names terms and aggregate blocking references with internal links, without exposing private student lists. The confirmation fingerprint includes status/revision and actual reference evidence; reference changes require another review. Lifecycle changes never cancel teaching automatically. Resolve uses through their owning workflow or defer the change; A does not add offering cancellation tooling.
- Inactive/graduated cohorts remain visible using status filters and in histories/existing referenced records. New placement requires active state. Existing routine, attendance and publication reads are not filtered away by current cohort status. Repeat means another term at the same semester; hold means no progression/placement for the destination term; both remain proposals for BAT-01B, with no new hold flag in A.

### D-4 — Per-term counts and migration

- Add per-placement count, verification metadata and revision. A value is null (unknown) or an integer 0–2,147,483,647. Zero is an explicitly entered count; blank is unknown. A numeric count can be **Unverified estimate** or **Verified**. Never infer verification from a number, roster length, old global value or term activation.
- **Save estimate** stores the number with no verifier/time; **Confirm count** requires a number, a short non-private source/reference (1–300 characters) and an explicit confirmation. Store current authorized actor and server instant; display Asia/Dhaka. **Return to unverified** clears current verifier/time, retains the value and records a reason. Editing a verified number without reconfirming makes it unverified; editing the source requires explicit reconfirmation. **Set unknown** clears current value and verification with a reason. No frontend-supplied actor/time is trusted. Every change preserves before/after evidence in the audit.
- Only the active term's count is editable in A, even after semester correction is frozen by academic use. Completed/draft/unknown-status term counts are read-only. Count changes show affected room-fit/conflict evidence before confirmation; they retain bookings and immediately recompute draft validation. They do not silently relocate classes or republish snapshots. A newly detected over-capacity booking is visibly blocked from unconditional publication by existing validation; retaining it is not a claim that it fits.
- Forward migration copies each valid existing global number to every **existing** placement as an explicitly unverified legacy estimate, with provenance that its historical term was never established. This retains numerical evidence, not a claim of historical verification. Null stays unknown. A legacy count with no placement remains in the retained legacy column and is shown to editors as an unassigned legacy value; migration invents no placement or term. Invalid negative values are retained as legacy evidence but not imported as valid estimates; flag them for a decision. Existing global column remains preserved but ceases to drive live operational calculations. No migration marks anyone verified, supplies an actor or rewrites a publication.
- Complete the migration on PGlite and PostgreSQL using populated synthetic pre-migration copies, null/non-null/zero/invalid/orphan/legacy-status and two-term fixtures. Preserve every old column, ID, historical row and snapshot hash, then exercise repeat preparation and recovery. New constraints apply to new writes without destructive normalization of legacy semester/status values. Stop on unsupported schema rather than repair institutional data implicitly. Institutional migration requires a later explicit backed-up operation.

### D-5 — Count consistency, safety and publications

- Every active/draft calculation joins a cohort count by **the teaching group's/offering's term**, never by whichever term is currently active or the global batch count. Apply this to active portal/meeting views, auto-schedule propose/apply, assignment validation, all-term room edit/lifecycle/maintenance evidence, conflict checks and new publication assembly. Keep missing-placement legacy offerings visible with unknown term count and an advisory.
- A numeric estimate remains usable as a planning estimate and retains existing over-capacity blockers. It always adds an unverified-count warning, even when its number fits the room. Unknown remains unknown. Confidence and arithmetic are separate: a group is verified only when all local audiences are verified and external audience evidence is sufficiently known under existing rules. An external numeric count is not silently awarded cohort verification metadata.
- Sum unique cohort IDs once per canonical shared group; add the existing external audience once. Unknown components prevent a complete total, but any known numeric subtotal already above room capacity must still block. No unverified/unknown count may produce an unconditional fit assertion. Preserve existing capability/maintenance/overlap and source publication gates; this slice does not change the existing warning/blocker publication policy.
- Count/identity updates recompute live draft evidence only. New snapshots freeze safe numerical count/confidence and validation warnings; verifier identities, source notes, revision/context tokens and raw audit never enter public JSON/HTML/CSV/print. Use backward-compatible optional confidence fields on newly generated schema-4 audience/batch records, explicitly whitelisted in frozen archive projections. Old schema 3/4 records without them retain legacy unspecified confidence; do not look it up live, retroactively label it verified or rewrite stored JSON. Unsupported schemas continue to fail safely. Regression-test public and archived teacher/official/CSV views against unchanged old snapshots.

### D-6 — Transactions, stale results and interface

- Reuse SET-01A context discipline: capture active ID + generation on placement/count forms and reject missing/stale/ABA context inside the real mutation transaction. Identity/lifecycle forms are explicit cohort operations with row revision, not active-term writes, but still lock term context before term-sensitive reference decisions. Lifecycle previews bind context generation and fresh all-term evidence. Never silently retarget old forms to a newly active term.
- Serialize these infrequent administrative cohort mutations using an exclusive term-context lock first, then target term/cohort/placement rows as needed, then room rows in ascending ID order. Check the submitted active context after obtaining that lock; do not take a shared lock and upgrade it. The lock alone does not advance generation: activation/reset retain their existing epoch semantics. Existing active reference/publication writers already hold shared context. Add shared context participation before domain locks to any remaining reference creators and room mutation paths that read count evidence. This makes their evidence atomic with cohort changes without introducing a separate advisory-lock system. Inventory actual writers before implementation, including seeds/preparation used only on owned targets.
- Composed live count reads must use a consistent shared-context transaction (or a proved equivalent snapshot/revision recheck) so a single response cannot mix pre-change batch counts and post-change meeting confidence. Review-only all-term evidence must also be self-consistent. Keep locks bounded and free of user/network waits. The exclusive lock briefly delays other active writes; this is the chosen correctness/simplicity tradeoff for low-frequency cohort administration. PostgreSQL independent requests and PGlite's actual queue must prove count/assignment, publish/delete/lifecycle and activation races, including both acquisition orders. Do not rely on per-browser action ordering.
- Authorize and parse every server entry point independently, rejecting duplicate/non-text scalar fields, invalid IDs, unknown statuses and forged ownership. Mutations, revision changes and audit insertion commit together. A failed audit rolls back the mutation. Unique conflicts and stale evidence return readable messages; no raw SQL/errors, success on refusal or loss of typed values. Revision checks apply to identity and each placement; view refresh alone is not concurrency control.
- `/batches` keeps active-term context, search and stream/lifecycle filters, with **Add batch** for editors. Detail separates identity/status, active-term placement/count, chronological placement history and editor-only change history. Use compact desktop rows and stacked mobile cards. **Not placed**, **Unknown**, **Estimate — unverified**, **Verified**, **Shared teaching**, **Inactive** and **Graduated** are distinct text states.
- Loading, empty/no matches, denied/not-found, pending, successful, field-error, duplicate, stale and blocked-review states preserve context and expose the next action. Use labelled fields, associated errors, focus management, keyboard-operable actions and announced feedback. No page-wide overflow at 1440/390/320px. Existing paper/ink/pine/gold design remains; the sketches are reviewable workflow proposals, not an implemented app.
