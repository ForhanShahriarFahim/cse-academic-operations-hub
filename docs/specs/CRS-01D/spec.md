# CRS-01D — Start class groups from a previous term

Parent: CRS-01 / #7, partially delivered. Updated 18 November 2026 (Asia/Dhaka).
Status: **Proposed.** [Approval and plan](plan.md) · [Inspection and verification](verification.md) · [Responsive sketch](mockups/index.html)

## Problem and inspected baseline

After preparing a term's cohorts and offerings, a coordinator can currently create its class groups only one at a time. Each group repeats decisions about who attends, who teaches, workload units and weekly coverage. A term can reuse those decisions where the new offerings and teacher availability support them.

Offerings can then be started using the previous term's stream and semester, because a cohort may have advanced. Group start comes after this and uses existing destination offerings. |

Teacher-managed rows use null weekly minutes with a stored meeting-count placeholder. A blanket copy would carry terms and conditions that need review. |

CRS-01C D-1 deferred the previous-term start and teacher comparison to this slice. |

## Outcome and scope

An editor picks an earlier term, reviews the groups that can be carried forward, selects whole groups and creates them in one save. The review compares the recorded teachers, workload units and crediting of uniquely matched existing groups. Manual create and edit remain available for groups that need a fresh decision.

This slice covers the Class groups entry point, a review and comparison page, an additive transaction, and its history receipt. Cohort preparation, offering changes, routine scheduling, enrollment, attendance, claims, public output and the older completeness report are separate work. The proposal uses the existing schema.

## Review and matching rules

- **Class groups** links to `/terms/[id]/groups/start` for editors of draft or active terms. An editor can revisit it after creating groups to see the comparison. The source selector shows eligible earlier terms and labels which is selected. An explicitly supplied invalid source is explained and must be replaced before apply. Changing source clears selections. A completed or legacy destination shows read-only; invalid term IDs return not-found. Unauthorized requests receive no review payload.
- Map source to destination on **catalog course ID plus stream and term placement semester**. A source audience needs a valid link and an offered source row (planned, open or completed). Its present-day cohort status is irrelevant to its historical placement. A destination match requires an existing planned/open offering with an active cohort and a valid placement. Out-of-semester offerings use the actual placement, as in CRS-01B. Course activity is a creation gate.
- Require one source audience and one eligible destination offering for each course/stream/semester used by the proposal. Two source audiences at the same slot for the same course, two destination candidates, invalid links, or competing projections make affected proposals ambiguous. Evaluate ambiguity before considering occupied destination offerings so an existing group never steers which cohort is matched. Never select the first match. For each projected group require distinct destination offering IDs. Show missing or conflicting cohorts with the reason.
- An exact existing destination group uses the same course and all and only the projected offerings, with no duplicate holders or broken links. It appears as **Already grouped** and is never selectable. If some or all of the matched offerings belong to different groups, show **Review audience** and link to the destination groups. Keep partly matched merged groups intact. An ungrouped destination offering with no source group or usable projection remains available for manual creation from the Class groups page.
- For a unique exact comparison, compare teacher IDs, their stored units in integer hundredths and the stored crediting methods. Show **Teachers carried** if all match, including the case where both groups have no teachers. Show **Teachers changed** with additions, removals, before/after units and crediting changes as applicable. A teacher's present-day status is a separate indicator. When allocations are missing key facts, duplicated or otherwise unusable, or there is no unique exact match, explain why the teacher comparison is unavailable. Destination-only groups should be visible as having no comparable previous group. Recompute from live records after edits. There is no migration to store comparison labels.
- For creation, reuse the single-group rules for course, offerings, assignable teachers, unit bounds, crediting, delivery and requirement. Refuse unsupported or mixed crediting data, unsupported requirement state, and invalid fixed requirements. For teacher-managed groups accept the existing null-minutes representation with no fixed target and validate against the destination rules. Show a vacancy when the source has zero recorded allocations. Do not derive teachers from meetings or drop an unavailable teacher, carry an external audience, copy notes, or infer units.
- Before applying, show selected group and merged-group counts, the reason field (1–300 plain-text characters), and projected totals per affected teacher including existing allocations. Advisory limits are warnings. Explain that groups will be unscheduled and that active-term changes affect workload and eligibility. Show no source, no destination offerings (link to offerings), no eligible groups, blocked rows, read-only, pending, validation, stale and saved states. Keep selection and reason after ordinary validation errors. On stale, refresh the review and require fresh selections. Show a result linking to Class groups and change history. The review is an internal preparation screen, with no new print format.

## Apply and history

- Before loading editor data or applying, authorize the existing capability in CSE scope. Validate the source, target, reason, review token and a nonempty list of distinct server-issued row identifiers. Derive copy values on the server. Reject forged or blocked selections as a whole.
- In one transaction take the shared term-context lock, lock source and destination term rows in ascending ID order, then lock relevant teacher rows in stable ID order before the final read. Follow the same lock order at every entry point that uses both term rows. Re-read the source eligibility and the reviewed input: source and destination placements, offerings and group links, group and allocation facts, requirements, course activity, teacher eligibility and the displayed totals/limits. If the server fingerprint differs, return stale without writes. Verify PostgreSQL races against single-group edits, offering changes, source edits, term lifecycle and teacher deactivation, including external allocations if they affect displayed totals.
- Insert the selected groups, links, requirements and allocations and write one `term_class_groups.start` event in the same transaction. The event records actor, source and destination terms, reason and per-group source/destination IDs, course, audience, delivery, requirement and allocations. Show the receipt in existing editor-only Class group history, with enough stored labels to read it after edits or removal. A stale, rejected or failed audit produces no new groups or event.
- Preserve all existing rows outside those inserts, including published snapshots and their export/print. New groups use the same workload, attendance-access and scheduling integrations as manually created groups. No term is activated and no timetable rows are created by apply.

## Acceptance criteria

| ID | Observable condition | Verification |
| --- | --- | --- |
| AC-01 | The correct editors can review, apply and read history for a draft or active destination. Unauthorized and revoked actors see no editor payload and cannot apply. Earlier-source default and eligibility, direct links and read-only states work independently of the active term. | Server/browser role and term matrix, including direct actions, invalid sources and equal/later dates. |
| AC-02 | Course/stream/semester projection handles progression, repetition, merged groups, absent and cancelled offerings, ambiguous slots, duplicate holders, and existing or partly occupied groups without guessing. | Pure fixtures and both-adapter checks, including the imported shape. |
| AC-03 | Each eligible group carries exact allocatable teacher IDs, units and methods, delivery and coverage. Vacancies can be selected. Unavailable teachers, outside audiences, unreconciled records and invalid legacy facts need manual review. | Pure validation and persisted round-trip checks on both adapters. |
| AC-04 | A unique exact match shows carried/changed teachers accurately, including changed units/crediting, added/removed teachers and vacancies. Reshaped or invalid groups have no misleading teacher diff. | Projection and browser checks before apply, after apply and after a manual edit. |
| AC-05 | Apply writes all and only the selected groups and a readable receipt. Repeated, malformed, forbidden, stale or competing applies cannot duplicate or partly write groups. Audit failure rolls back all rows. | Both-adapter scenarios, independent PostgreSQL connections and row/event assertions. |
| AC-06 | Existing tables, groups and historical outputs are preserved. Workload totals, eligibility and routine availability for new groups follow existing rules. | Row fingerprints, archived CSV/A4 parity, focused class-group/offerings/rollover and history/eligibility regressions. |
| AC-07 | Review, selection summary, warning, validation, stale and receipt flows are usable at 1440/390/320 widths with keyboard and announced feedback. | Guarded synthetic compiled-browser review, axe and captures. |
| AC-08 | Required build and regression checks have an accurate recorded result. | Typecheck, lint, domain, default build and focused safety groups. Record any build exception separately for acceptance. |
